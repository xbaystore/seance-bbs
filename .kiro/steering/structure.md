# Structure — Séance BBS

## Repository layout

```
seance-bbs/
├── index.html                  # the whole site, one page
├── styles.css                  # CRT theme + contrast mode
├── app.js                      # all behavior (Store, SeedData, Boot,
│                               #   Router/Screens, GhostEngine)
├── README.md                   # pitch, run instructions, gallery index
├── LICENSE                     # MIT
├── .gitignore                  # OS/editor noise only — never .kiro
├── assets/
│   └── art/                    # canonical ANSI/ASCII art sources (.txt)
│       ├── seance-logo.txt
│       ├── haunted-house.txt
│       ├── modem.txt
│       ├── the-sysop.txt
│       ├── pumpkin-mainframe.txt
│       └── rip-floppy.txt
└── .kiro/
    ├── specs/seance-bbs/       # requirements.md, design.md, tasks.md
    ├── steering/               # product.md, tech.md, structure.md
    └── hooks/                  # *.kiro.hook agent hooks
```

## Conventions

- **Three-file app.** New behavior goes into `app.js` under the matching
  banner section; new presentation into `styles.css`. Do not create new
  JS/CSS files without updating the spec (`design.md`) first — the
  three-file shape is a stated design constraint, not an accident.
- **`app.js` sections, in file order:** `Store` → `SeedData` →
  `BootSequence` → `Router`/`Screens` → `GhostEngine` → boot/init call at
  the very bottom. Each section opens with a banner comment naming it.
- **Naming:** camelCase for JS functions/variables, `UPPER_SNAKE` for
  seed/constant data (`SEED_BOARDS`, `GHOST_POOLS`), kebab-case for CSS
  classes (`.screen-boards`, `.post--ghost`) and file names.
- **IDs and slugs:** board ids are short slugs (`general`, `hardware`,
  `parlor`); runtime ids for posts/entries are generated by the Store
  (`Date.now().toString(36)` + counter). Slugs appear in hash routes, so
  they are lowercase `[a-z0-9-]` only.
- **Routes:** `#/`, `#/boards`, `#/board/:slug`, `#/thread/:id`,
  `#/log`, `#/gallery`, `#/art/:id`, `#/settings`. Any new screen must
  register a route here and in `design.md`.

## Seed data & art assets

- Seed content lives in `app.js` (`SeedData` section). It is *shipped
  data*, edited like code: keep voices in character (see `product.md`
  tone rules) and dates relative to first run.
- Artwork is authored as plain-text files in `assets/art/` (one piece per
  `.txt` file, filename = art slug). The shipped copies are inlined into
  `SEED_ART` in `app.js` because the app makes no runtime fetches; the
  `.txt` files are the canonical editing source, and the README's gallery
  index must list exactly the pieces in `assets/art/` (the
  `readme-sync` hook helps keep this honest).
- Art files: preserve trailing spaces where they matter to the drawing,
  keep lines ≤ 80 columns (period-accurate), and note the artist handle
  and year in the README index, matching `SEED_ART` metadata.

## Documentation duties

- `README.md` is the judges' front door: pitch, feature list, run
  instructions, gallery index, and the "Built with Kiro" section. Any
  shipped feature change updates the README in the same commit.
- Specs are living documents during the build: if implementation forces a
  design change, edit `design.md`/`tasks.md` rather than letting them
  drift — the `.kiro` folder is judged as evidence of how Kiro was used.
